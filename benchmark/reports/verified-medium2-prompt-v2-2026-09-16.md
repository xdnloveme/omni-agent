## 发现与责任边界

1. **补丁没有满足全部回归契约。** 最终仅修改 `django/db/models/deletion.py`，在删除前按模型合并 fast_deletes。官方新增功能测试通过，但 `test_large_delete` 和 `test_large_delete_related` 失败，分别为查询数 22/25 和 23/26（实际/预期）。这证明官方回归要求未满足，不能仅凭这两条失败断言发生数据误删或所有批处理都错误。Agent 自行运行的 365 项相关测试也已暴露相同两项失败，之后没有修复补丁。
2. **重复取证仍存在。** 第 626.9 秒运行 delete 并截取末尾；第 634.0 秒未修改代码又运行同套测试以提取失败名称。另有初次未选题目 Python 环境后纠正、5 次 grep 输入错误、1 次超限 timeout 输入和 1 次缺少写范围声明。7 条工具 isError 不包含被 shell 管道掩盖退出码的测试失败。
3. **Core 终态存在明确语义缺口。** `packages/core/src/agent/loop/orchestrator.ts` 的 `stopReason !== "toolUse"` 分支统一返回 completed。虽然 `isFinalTextResponse` 不将 length 标为 final_response，但仍发 done，最终形成 run.completed 和进程返回 0。本次最后模型响应 stopReason=length、输出 16,384，未形成最终回复，仍被记录 completed。现有截断响应测试也只保证不发 final_response，并期待 done，因此全部单测通过并不覆盖正确的截断运行终态。

第 3 项归属 Core 的模型终止原因到 Run 终态转换；App/CLI/benchmark 应消费真实终态，不应在下游根据 token 数猜测失败。后续应明确区分正常 stop、输出截断及其他非正常原因，并用完整事件/状态链测试验证。是否允许续跑、续跑预算和消息语义是另外的行为决策；不应为掩盖终态问题直接加入隐式重试。本次保持实验变量单一，没有顺手修改跨层生命周期，也没有追加付费运行。
